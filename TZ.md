# Техническое задание — «Сумо-дайджест» (Python + GitHub Actions)

Замена Notion-агента на воспроизводимый пайплайн: сбор статей — Python, текст выпуска — LLM,
публикация — статический сайт на GitHub Pages.

Исходная спецификация агента: `docs/sumo-digest-agent-spec.md`. Всё, что здесь не оговорено,
берётся оттуда без изменений.

---

## 1. Границы

**В объёме:**
- ежедневный/по расписанию сбор статей из закрытого списка источников;
- отбор, дедупликация и написание выпуска моделью через Anthropic API;
- валидация выпуска (схема, ссылки, транслитерация);
- рендеринг статического сайта: индекс выпусков + страницы выпусков + Atom-фид;
- накопление таблицы «Новые имена и термины» в репозитории.

**Вне объёма (первая версия):**
- email-рассылка, формы подписки и отписки (см. §12);
- ручная редактура выпуска перед публикацией;
- полнотекстовый поиск по архиву.

---

## 2. Архитектура

```
GitHub Actions (cron)
   │
   ├─ 1. collect      config/sources.yml → список URL статей
   │                  (RSS, где есть; иначе ссылки из листинга по regex)
   │
   ├─ 2. extract      HTML статьи → чистый текст + дата + заголовок
   │                  фильтр: только новее даты прошлого выпуска, не в state.seen
   │
   ├─ 3. select       LLM #1: корпус заголовков+лидов → отобранные id, склейка дублей
   │                  (при малом корпусе шаг пропускается)
   │
   ├─ 4. write        LLM #2: полные тексты отобранных статей → digest.json
   │                  структурированный вывод по schema/digest.schema.json
   │
   ├─ 5. validate     схема → ссылки ⊆ корпус → линтер транслитерации
   │                  провал = выпуск не публикуется, Actions падает
   │
   ├─ 6. render       digest.json → Jinja2 → HTML + Atom
   │
   └─ 7. publish      commit: выпуск, state.json, new_terms.csv → GitHub Pages
```

Ключевой инвариант: **модель не имеет сетевого доступа.** Ни web_search, ни web_fetch,
ни MCP. Всё, что она видит, приходит из шага 2. Если этот инвариант нарушить, закрытый
список источников из спецификации перестаёт что-либо гарантировать.

## 3. Модули

### 3.1. `collect.py`

Вход: `config/sources.yml`, `data/state.json`.
Выход: `list[ArticleRef]` — `{source_id, url, title_hint, published_hint}`.

- Для каждого источника: если задан `rss` — читать его; иначе загрузить `listing_url`
  и собрать `<a href>`, подходящие под `link_pattern`.
- Порядок обхода — строго по `priority` из конфига. Sponichi и Hochi обходятся всегда
  и первыми (спецификация §8: без них выпуск теряет фактуру).
- Ошибка источника (таймаут, 4xx, 5xx, пустой листинг) — **не ретраить**, записать
  `status: failed` и идти дальше. Это прямое требование спецификации.
- Таймаут на запрос: 15 с. Общий бюджет шага: 120 с.
- User-Agent — осмысленный, с контактом. `robots.txt` уважать.
- Дедупликация по нормализованному URL (без query и fragment).

### 3.2. `extract.py`

Вход: `list[ArticleRef]`. Выход: `list[Article]`.

- Загрузка HTML статьи, извлечение основного текста универсальным экстрактором
  (`trafilatura` — работает на японских новостных сайтах; проверить на этапе E1).
  Селекторы под каждое издание не писать: они ломаются чаще, чем регэксп на ссылки.
- Дата публикации берётся из метаданных страницы (`article:published_time`, JSON-LD,
  `<time datetime>`). Если даты нет — статья помечается `date_confidence: low`
  и модель обязана не указывать дату в блоке. Придуманные моделью даты — недопустимы.
- Отсев: `published < last_issue_date`, `url in state.seen`, длина текста < 200 символов.
- Текст японских статей **не переводить** на этом шаге. Модель читает оригинал —
  это требование спецификации (пересказы теряют детали).
- Ограничение корпуса: не более `max_articles` (по умолчанию 12) — по приоритету
  источника, затем по свежести. Это не бюджет браузинга, а контроль стоимости токенов.

### 3.3. `llm.py` — шаг select (опциональный)

Запускается, если статей в корпусе > 12. Модель получает `id + заголовок + первые
300 символов` каждой статьи и возвращает `{"selected": [id], "duplicates": [[id, id]]}`.
Дешёвая модель (Haiku). При корпусе ≤ 12 шаг пропускается — платить за отбор из
двенадцати статей смысла нет.

### 3.4. `llm.py` — шаг write

- Системный промпт: `prompts/write.md` (переписанная версия §1 спецификации —
  из неё убраны все инструкции про обход сайтов, добавлены правила работы с корпусом).
- Отдельным блоком в контекст подаётся руководство по транслитерации (§3 спецификации)
  целиком, файлом `prompts/translit_guide.md`. Кешировать через prompt caching:
  документ большой и не меняется от запуска к запуску.
- Пользовательское сообщение: период, дата прошлого выпуска, JSON-массив статей
  (`id`, `source_name`, `url`, `published`, `date_confidence`, `title`, `text`).
- Вывод — строго по `schema/digest.schema.json`, через tool use / structured output.
  Свободный текст с последующим парсингом JSON из markdown-блока не использовать:
  это отдельный источник отказов на пустом месте.
- Модель: `claude-sonnet-5` для write, `claude-haiku-4-5` для select. Строки моделей
  сверить с актуальной документацией API перед первым запуском.
- `temperature`: 0.3. Ретрай при ошибке API — 2 раза с экспоненциальной паузой.

### 3.5. `validate.py` — три уровня

**Уровень 1 — схема.** Валидация `digest.json` по JSON Schema. Провал = стоп.

**Уровень 2 — ссылки и факты.**
- каждый `sources[].url` в каждом блоке обязан присутствовать в корпусе шага 2.
  Ссылка, которой нет во входных данных, — галлюцинация. Провал = стоп;
- каждый `sources[].name` соответствует `source_id` этого URL из конфига;
- `blocks[].date` не позже даты выпуска и не раньше начала периода;
- блок, у которого исходная статья была `date_confidence: low`, не должен содержать дату;
- количество блоков в диапазоне 5–10, либо `quiet_period: true` (межсезонье).

**Уровень 3 — линтер транслитерации.** `config/translit_rules.yml`:
- `forbidden` — пары «неверно → верно» из §3.4 спецификации («одзэки» → «озеки»,
  «хэя» → «бейя», «сисё»/«шишо» → «ояката», «банзукэ» → «бандзуке», «Хосёрю» → «Хошорю»
  и т. д.). По умолчанию — **автозамена с записью в лог**, не отказ: это механические
  ошибки с однозначным исправлением;
- `patterns` — регулярки на классы ошибок (латиница внутри кириллического слова,
  макроны, знаки ударения). Эти — отказ, автоматически чинить нельзя;
- `canonical` — словарь имён из §3.2 спецификации. Если в тексте встречается имя,
  отличающееся от канонического на одну-две буквы, — предупреждение в лог выпуска.

Отдельная проверка: каждое имя рикиши при первом упоминании сопровождается японским
написанием в скобках либо пометкой «romaji: … — требует проверки». Реализуется
эвристикой; при провале — предупреждение, не отказ (эвристика будет ошибаться).

### 3.6. `render.py`

Jinja2. Шаблоны в `templates/`:
- `issue.html` — страница выпуска: строка периода, «Главное», блоки, «Мимо кассы»,
  дисклеймер про ИИ-генерацию из §6.1 спецификации;
- `index.html` — витрина: описание, список выпусков от новых к старым;
- `atom.xml` — фид, полный текст выпуска в `<content>`.

Оформление — минимальное и читаемое: один CSS-файл, без сборщиков, без JS.
Японские иероглифы в скобках требуют шрифта с поддержкой CJK — задать fallback явно.

### 3.7. `state.py`

`data/state.json`:
```json
{
  "last_issue_date": "2026-09-10",
  "last_issue_slug": "2026-09-10",
  "seen_urls": ["sha1:...", "..."],
  "seen_urls_kept_days": 30
}
```
Коммитится обратно в репозиторий тем же workflow. Без состояния каждый выпуск
будет пересказывать статьи предыдущего — при ежедневном запуске это заметно сразу.

`data/new_terms.csv` — накопитель новых имён (§5 спецификации): модель возвращает их
в `digest.json`, пайплайн дописывает в CSV, дубли по колонке «Оригинал» не добавляет.
В текст выпуска таблица не попадает.

## 4. Конфигурация источников

`config/sources.yml` — единственное место, где перечислены источники. Добавление
источника кодом или промптом запрещено (§8 спецификации: Asahi и Nikkei исключены
навсегда, возвращать «на всякий случай» нельзя).

Поля: `id`, `name`, `priority`, `listing_url`, `rss` (опционально), `link_pattern`
(regex для отбора ссылок статей из листинга), `lang`, `enabled`.

`link_pattern` для каждого источника проверяется на этапе E0 вручную — по одному
живому листингу. Это единственная site-specific часть системы.

---

## 5. Схема выходного JSON

См. `schema/digest.schema.json`. Основные поля:

| Поле | Смысл |
| --- | --- |
| `issue_date` | дата выпуска, ISO |
| `period.from` / `period.to` | охваченный период |
| `sources_reviewed[]` | `{name, status: ok\|partial\|failed, articles_used}` — источник строки периода |
| `lead` | «Главное», 2–3 предложения |
| `blocks[]` | `{date?, place, subtitle, body, category, importance, sources[]}` |
| `missed` | «Мимо кассы», одна строка |
| `new_terms[]` | `{original, romaji, russian, status}` |
| `quiet_period` | true для межсезонья — снимает требование 5–10 блоков |

`category` — enum из порядка сортировки спецификации: `makuuchi_juryo`, `banzuke`,
`injury`, `training`, `lower_divisions`, `other`. Сортировка блоков выполняется
**кодом** по `(category_rank, importance, date)`, а не моделью. Модель систематически
ставит первым то, о чём написала подробнее, а не то, что важнее.

## 6. GitHub Actions

`.github/workflows/digest.yml`:
- `schedule`: по умолчанию `0 5 * * 1,4` (UTC) ≈ 08:00 по Кишинёву летом.
  Переход на зимнее время даст сдвиг на час — это допустимо. Для ежедневного режима:
  `0 5 * * *`;
- `workflow_dispatch` с входами `period_from`, `dry_run` — для ручного прогона и отладки;
- шаги: checkout → setup-python → install → `python -m sumo_digest.run` →
  commit артефактов → deploy Pages;
- при провале валидации: job падает, ничего не коммитится, выпуск не публикуется,
  в Actions остаётся артефакт `digest.raw.json` и лог для разбора;
- права: `contents: write`, `pages: write`, `id-token: write`;
- секрет: `ANTHROPIC_API_KEY`.

Конкурентность: `concurrency: sumo-digest` — чтобы ручной запуск не столкнулся с cron.

## 7. Поведение при вырожденных случаях

| Ситуация | Поведение |
| --- | --- |
| Ни один источник не открылся | Выпуск не создаётся, job падает с внятным сообщением. Публиковать пустую страницу нельзя. |
| Открылись только низкоприоритетные | Выпуск создаётся, в строке периода перечислены недоступные источники (требование спецификации). |
| Статей меньше 5 | Модель ставит `quiet_period: true`, пишет короткий выпуск про подготовку к басё/дзюнгё. Валидатор пропускает. |
| Модель вернула невалидный JSON | 2 ретрая, затем отказ. |
| Ссылка в выпуске отсутствует в корпусе | Отказ без ретрая — это не сбой, а признак того, что промпт разъехался. |
| Источники противоречат друг другу | Требование спецификации: привести оба варианта с указанием издания. Проверяется вручную при приёмке, автоматически — нет. |

## 8. Стек

Python 3.12. `httpx`, `trafilatura`, `PyYAML`, `jsonschema`, `Jinja2`, `anthropic`,
`feedparser` (если у источников найдутся RSS). Тесты: `pytest`. Линт: `ruff`.
Зависимости фиксируются (`uv` или `pip-tools`) — иначе выпуск начнёт ломаться от
обновлений `trafilatura` в случайный день.

## 9. Тестирование

Сеть в тестах запрещена. Все тесты — на фикстурах:
- `tests/fixtures/listings/*.html` — сохранённые листинги для проверки `link_pattern`;
- `tests/fixtures/articles/*.html` — для проверки экстракции текста и даты;
- `tests/fixtures/digest_*.json` — валидные и намеренно битые выпуски для валидатора;
- линтер транслитерации: таблица «на входе — на выходе» из §3.4 спецификации.

Отдельный smoke-скрипт `scripts/check_sources.py` ходит по всем листингам вживую
и печатает, сколько ссылок нашлось. Запускать вручную раз в месяц или при подозрении,
что источник сменил вёрстку. Автоматически в CI не гонять.

## 10. Стоимость и наблюдаемость

Оценка на выпуск: ~12 статей × ~3 000 токенов японского текста ≈ 40 000 входных
токенов + руководство по транслитерации (кешируется). Выход — 3–5 тысяч токенов.
При двух выпусках в неделю это единицы долларов в месяц; при ежедневном — кратно больше,
но всё ещё немного.

Логировать в артефакт каждого запуска: статусы источников, количество статей на входе,
использованные токены, сработавшие правила линтера, время шагов. Без этого невозможно
понять, почему выпуск стал хуже.

## 12. Рассылка (отдельный, необязательный этап)

Atom-фид и Telegram-канал закрывают доставку без бэкенда и без обработки персональных
данных. Email-рассылка требует: формы (то есть внешнего сервиса или бэкенда), хранения
адресов, механизма отписки в каждом письме, основания обработки и информирования
субъектов. Это отдельный проект, а не шаг в этом пайплайне.

Если email всё-таки нужен — брать готовый сервис (Buttondown, Listmonk) и отдавать ему
Atom-фид, а не писать хранение подписчиков самому.
