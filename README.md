# Сумо-дайджест

Автоматический обзор новостей профессионального сумо на русском языке.
Раз в сутки GitHub Actions собирает статьи из закрытого списка японских и англоязычных
изданий, отдаёт их модели Claude, получает выпуск в виде JSON и публикует его
статической веб-страницей на GitHub Pages.

Проект заменяет ИИ-агента, который раньше жил в Notion. Поведение агента —
источники, правила отбора, транслитерация, формат выпуска — целиком описано
в [`sumo-digest-agent-spec.md`](sumo-digest-agent-spec.md); этот файл остаётся
источником истины для промптов.

## Как это работает

Конвейер из четырёх шагов, каждый следующий работает только с результатом предыдущего:

```
1. collect   Python скачивает разделы источников и статьи      → сырые тексты
2. digest    один вызов Claude API со структурированным выводом → JSON выпуска
3. lint      проверка транслитерации и обязательных полей       → JSON + список замечаний
4. render    Jinja2 собирает HTML + индекс + RSS                → docs/ → GitHub Pages
```

Ключевые решения и почему они такие:

**Страницы скачивает Python, а не модель.**
Спецификация требует закрытого списка источников и прямо запрещает веб-поиск
(раздел 8: «запрет веб-поиска — жёсткое правило»). Когда обход делает код,
список источников физически невозможно обойти: модель видит только тот текст,
который ей передали. Плюс это даёт детерминированный бюджет обхода
(3–4 раздела, до 8 статей), кэш скачанного, дешёвые повторные прогоны при отладке
промпта и возможность тестировать отбор на сохранённых страницах без обращения к API.
Извлекать текст планируется универсальным способом (readability-подход),
без отдельных парсеров под каждый сайт — иначе девять источников превращаются
в девять постоянно ломающихся парсеров.

*Альтернатива, если универсальное извлечение окажется негодным:* серверный инструмент
`web_fetch` Claude API с `allowed_domains` по списку источников и без `web_search`.
Тогда закрытый список гарантируется на стороне API. Минус — обход перестаёт быть
воспроизводимым и его сложнее отлаживать.

**Модель делает только редакторскую работу.**
Отбор значимого, отсев дублей, сортировка по важности, перевод, транслитерация,
текст блоков. Никакой вёрстки, дат по памяти и выдуманных ссылок: ссылки берутся
из того, что собрал шаг 1.

**Ответ модели — JSON по схеме, а не размеченный текст.**
Используется structured output (`output_config.format` с JSON-схемой), поэтому
ответ гарантированно валиден и его не нужно разбирать регулярками.
HTML собирается из этого JSON шаблонами Jinja2 — вёрстка меняется без перезапуска модели,
а старые выпуски можно перерендерить.

**Транслитерация проверяется кодом, а не только промптом.**
Руководство из раздела 3 спецификации передаётся в системном промпте (стабильный
префикс → prompt caching), но поверх этого шаг `lint` ищет запрещённые написания
(«одзэки», «хэя», «Хосёрю», «дзи» вместо «джи» и т. д.) по словарю замен.
Это главный источник ошибок агента, и он единственный, который можно проверить детерминированно.

**Новые имена копятся в репозитории.**
Раздел 5 спецификации (рабочая таблица «Новые имена и термины») становится файлом
данных, который выпуск дополняет автоматически. Подтверждённые имена вручную
переносятся в справочник и попадают в промпт следующего выпуска.

### Схема JSON — контракт между моделью и рендерером

Черновой вид (окончательная схема появится в `schema/digest.schema.json`):

```jsonc
{
  "issue_date": "2026-09-10",
  "period": { "from": "2026-09-07", "to": "2026-09-10" },
  "sources_seen": [
    { "name": "Sponichi", "url": "https://…", "status": "ok" }        // ok | headlines_only | failed
  ],
  "lead": "2–3 строки: самое важное за период",
  "blocks": [
    {
      "date": "2026-09-09",
      "place": "Рёгоку Кокугикан",
      "headline": "…",
      "body": "2–5 предложений",
      "category": "makuuchi",                                          // порядок сортировки из спецификации
      "importance": 5,
      "sources": [ { "name": "Nikkan Sports", "url": "https://…" } ],
      "names": [ { "ru": "Киришима", "ja": "霧島", "romaji": "Kirishima", "needs_check": true } ]
    }
  ],
  "skipped": ["темы, сознательно не вошедшие — раздел «Мимо кассы»"],
  "new_terms": [ { "original": "音羽山", "romaji": "Otowayama", "ru": "Отоваяма", "status": "требует проверки" } ]
}
```

`new_terms` в текст выпуска не попадает — только в файл данных, как требует спецификация.

## Структура репозитория (план)

```
sumo-digest-agent-spec.md      спецификация агента: промпты, источники, транслитерация, формат
src/sumo_digest/
  collect.py                   обход разделов источников и статей, бюджет обхода, кэш
  digest.py                    вызов Claude API, сборка промпта, structured output
  lint.py                      проверка транслитерации и полноты выпуска
  render.py                    JSON → HTML, индекс выпусков, RSS
  models.py                    схема выпуска (Pydantic)
prompts/
  system.md                    системный промпт (раздел 1 спецификации)
  transliteration.md           руководство по транслитерации (раздел 3)
data/
  sources.yaml                 закрытый список источников с приоритетами
  new-terms.json               накопитель новых имён (раздел 5)
  issues/YYYY-MM-DD.json       сырой JSON каждого выпуска
templates/                     Jinja2: выпуск, индекс, RSS
docs/                          готовый сайт, отдаётся GitHub Pages
tests/                         тесты на сохранённых страницах и сохранённых ответах модели
.github/workflows/digest.yml   ежедневный запуск по расписанию + ручной запуск
```

## Конфигурация (план)

| Переменная | Обязательна | Где взять | Что сломается без неё |
| --- | --- | --- | --- |
| `ANTHROPIC_API_KEY` | да | console.anthropic.com → API keys; в GitHub кладётся в Secrets репозитория | шаг `digest` не запустится |

Всё остальное — параметры запуска и файлы данных, не секреты: список источников
в `data/sources.yaml`, модель и бюджеты — в конфиге проекта.

Модель по умолчанию — `claude-opus-5` (контекст 1M, adaptive thinking).
Выпуск целиком помещается в один вызов, поэтому дробить его на несколько запросов не нужно.

## Расписание и публикация

- Workflow запускается по cron ежедневно и вручную (`workflow_dispatch`).
- Период выпуска считается **от даты предыдущего выпуска до сегодня**, а не
  фиксированными семью днями, — так расписание можно менять, не трогая промпт.
- Если за период нет значимых новостей (межсезонье), выпуск выходит коротким
  с пометкой «спокойный период» — так требует спецификация.
- Готовый сайт лежит в `docs/` и отдаётся GitHub Pages; workflow коммитит его
  обратно в репозиторий (нужны права `contents: write`).
- Рассылка по email из Notion-версии заменяется RSS-лентой: она не требует
  базы подписчиков, форм согласия и обработки отписок.

⚠️ **Расхождение со спецификацией.** В спецификации расписание — понедельник и четверг
(раздел 0, раздел 7.1). Здесь заложен ежедневный запуск. При ежедневном выпуске
новостей за сутки обычно меньше, чем 5–10 блоков из формата, поэтому нижняя граница
объёма станет мягкой: сколько есть значимого, столько и блоков. Если это неудобно —
меняется одна строка cron.

## Что заменяет прежнего Notion-агента

| Было в Notion | Стало здесь |
| --- | --- |
| Страница-скилл с системным промптом | `prompts/system.md` под контролем версий |
| Страница руководства по транслитерации | `prompts/transliteration.md` + автопроверка в `lint.py` |
| Черновик «Новые имена и термины» | `data/new-terms.json`, дополняется автоматически |
| Страницы выпусков + индекс | `docs/` на GitHub Pages + `data/issues/*.json` |
| Базы подписчиков и отказов, две формы | RSS-лента |
| Триггер платформы (пн/чт) | GitHub Actions cron |
| Инструмент fetch платформы | `collect.py` (или серверный `web_fetch`) |

## Ограничения и риски

- **Cron в GitHub Actions неточен.** Запуск регулярно сдвигается на десятки минут
  под нагрузкой, отдельные запуски могут пропускаться. Для дайджеста это некритично,
  но «выпуск ровно в 8:00» обещать нельзя. Кроме того, в публичных репозиториях
  расписания отключаются после длительной неактивности репозитория — при
  публичном репозитории это нужно проверить отдельно.
- **Источники ломаются молча.** Смена вёрстки, таймаут, платный доступ. Спецификация
  требует не повторять попытку, а отметить недоступный источник в строке периода —
  статус каждого источника входит в JSON и печатается на странице.
- **Sponichi и Hochi обязательны.** Если оба не открылись, выпуск лучше не публиковать:
  по опыту прежних выпусков оттуда приходит основная фактура.
- **Транслитерация.** Автопроверка ловит известные ошибки по словарю; новые имена
  она поймать не может — они помечаются «требует проверки» и проверяются человеком.
- **Модель может ошибиться в фактах и датах.** Под каждым блоком есть ссылки
  на первоисточники, на индексной странице стоит предупреждение, что выпуски
  готовит ИИ без ручной редактуры.

## Стоимость

Один выпуск — один вызов модели. Порядок величины при `claude-opus-5`
($5 за 1M входных токенов, $25 за 1M выходных): обход 8 статей даёт примерно
100–150 тыс. входных токенов, выпуск — 6–10 тыс. выходных, то есть **порядка $0.7–1.0
за выпуск** до кэширования промпта. Системный промпт с руководством по транслитерации
стабилен и кэшируется, что заметно снижает входную часть при ежедневных запусках.
Точная цифра будет видна из `usage` первого же реального прогона — эти числа
пока оценочные.

## Этапы

1. **Каркас.** `sources.yaml`, `collect.py`, кэш скачанного, сохранённые страницы для тестов.
2. **Выпуск.** Схема JSON, промпты из спецификации, `digest.py`, первый ручной прогон.
3. **Качество.** `lint.py` со словарём запрещённых написаний, приёмочный чек-лист
   из раздела 7.3 спецификации в виде тестов.
4. **Публикация.** Шаблоны, индекс, RSS, GitHub Pages.
5. **Автоматизация.** Workflow по расписанию, коммит результата, отчёт о недоступных источниках.

## Открытые вопросы

- ⚠️ Ежедневно или, как в спецификации, по понедельникам и четвергам?
- ⚠️ Репозиторий публичный или приватный? От этого зависит и GitHub Pages, и поведение cron.
- ⚠️ Нужна ли email-рассылка помимо RSS (потребует внешнего сервиса и хранения адресов)?
- ⚠️ Есть ли у источников RSS-ленты — проверяется на первом этапе; где есть, обход по ним надёжнее HTML.
