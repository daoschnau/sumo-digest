# Сумо-дайджест

Обзор новостей профессионального сумо на русском языке. Дважды в неделю GitHub Actions
собирает статьи из закрытого списка японских и англоязычных изданий, отдаёт корпус
модели, получает структурированный JSON, проверяет его и публикует выпуск
на статическом сайте.

Проект заменяет ИИ-агента, который раньше жил в Notion.

## Статус

**E0 не начат.** В репозитории есть конфигурация, промпты, схема выпуска и workflow;
Python-пакета `sumo_digest` ещё нет, поэтому команды из раздела «Запуск» пока
не работают. Расписание в workflow намеренно закомментировано до этапа E5 —
иначе прогоны падали бы дважды в неделю.

## Как это работает

```
GitHub Actions (cron, пн/чт)
  1. collect    config/sources.yml → ссылки на статьи (RSS или regex по листингу)
  2. extract    HTML → текст, дата, заголовок; отсев по дате и по seen_urls
  3. select     LLM #1 (только если корпус > 12): что берём, что дубли
  4. write      LLM #2: корпус → digest.json по schema/digest.schema.json
  5. validate   схема → ссылки ⊆ корпус → линтер транслитерации
  6. render     Jinja2 → HTML выпуска, индекс, Atom
  7. publish    коммит выпуска и состояния → GitHub Pages
```

Три решения, на которых всё держится:

**У модели нет сети.** Ни `web_search`, ни `web_fetch`, ни MCP. Модель видит только
корпус, собранный Python. Спецификация запрещает веб-поиск — если оставить обход
за моделью, запрет остаётся строчкой в промпте, которую нечем проверить. Так он
становится свойством системы.

**Ни одна ссылка не публикуется непроверенной.** Каждый URL из выпуска обязан
присутствовать во входном корпусе. Не совпало — выпуск не публикуется. Правдоподобный
несуществующий URL — самая дорогая ошибка такой системы: читатель идёт проверить факт
и упирается в 404.

**Транслитерация проверяется кодом.** По §8 спецификации это главный источник ошибок.
Раздел 3.4 фактически описывает линтер, и он сделан детерминированным
(`config/translit_rules.yml`): однозначные ошибки чинятся автозаменой с записью в лог,
неоднозначные — отказ.

## Структура

```
config/sources.yml           закрытый список источников: приоритет, листинг, link_pattern
config/translit_rules.yml    правила линтера: autofix / reject / warn + канонические имена
schema/digest.schema.json    контракт выходного JSON
prompts/write.md             системный промпт писателя выпуска
prompts/select.md            системный промпт отборщика
data/state.json              дата прошлого выпуска и seen_urls, коммитится пайплайном
data/new_terms.csv           накопитель новых транслитераций (§5 спецификации)
docs/                        исходная спецификация агента
.github/workflows/digest.yml сборка и публикация; расписание включается на E5
```

Появится по ходу этапов: `src/sumo_digest/` (E1–E4), `templates/` и `site/` (E4),
`tests/` и `scripts/check_sources.py` (E0–E1), `pyproject.toml` (E0),
`prompts/translit_guide.md` — §3 спецификации отдельным файлом для prompt caching (E2).

## Запуск

⚠️ Команды заработают начиная с E1 — пакета `sumo_digest` пока нет.

```bash
uv sync                                  # установка
python -m sumo_digest.collect --dry-run  # только сбор корпуса, без LLM
python -m sumo_digest.run --dry-run      # полный прогон без публикации
python scripts/check_sources.py          # живая проверка листингов, вручную
pytest                                   # тесты (только на фикстурах, без сети)
```

## Конфигурация

| Переменная | Обязательна | Что сломается без неё |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | да | шаги select и write |
| `SUMO_DIGEST_MODEL` | нет | переопределяет модель шага write |
| `SUMO_DIGEST_DRY_RUN` | нет | `1` — не коммитить и не публиковать |

В GitHub ключ кладётся в Secrets репозитория под именем `ANTHROPIC_API_KEY`.
В коде и в документации ключей нет и быть не должно.

Ключ создаётся привязанным к аккаунту (personal key) и **со скоупом на Default
Workspace**. Ключ без привязки к пространству требует заголовка
`anthropic-workspace-id` в каждом запросе, иначе API отвечает 400, — со скоупом
он не нужен. Срок жизни — Never: ключ лежит в секретах и ротируется вручную,
а истёкший ключ починить нельзя, только выпустить новый.

## Расписание и публикация

- `0 5 * * 1,4` UTC ≈ 08:00 по Кишинёву летом, 07:00 зимой. Включается на E5.
- Период выпуска — от даты прошлого выпуска (`data/state.json`) до сегодня,
  а не фиксированные семь дней.
- Ручной прогон — `workflow_dispatch` с входами `period_from` и `dry_run`.
- Провал валидации: job падает, ничего не публикуется, в артефактах остаются
  `digest.raw.json`, корпус и лог.
- Доставка — Atom-фид; email вынесен в необязательный этап E7 вместе с Telegram
  (§12 ТЗ: хранение адресов — отдельный проект с персональными данными).

## Стоимость

Порядка 40 000 входных токенов на выпуск (≈12 статей японского текста) плюс
кешируемое руководство по транслитерации, 3–5 тысяч выходных. При двух выпусках
в неделю — единицы долларов в месяц. Точная цифра будет видна из `usage`
первого реального прогона.

## Ограничения

- **Листинги ломаются при редизайне.** `link_pattern` — единственная site-specific
  часть системы; проверяется вручную скриптом `scripts/check_sources.py`.
- **Sponichi и Hochi обязательны** — по §8 спецификации оттуда приходит основная
  фактура. Если не открылись оба, выпуск лучше не публиковать.
- **Cron в GitHub Actions неточен** — сдвиг на десятки минут под нагрузкой,
  отдельные запуски пропускаются.
- **Выпуски готовит ИИ без ручной редактуры.** Под каждым блоком ссылки
  на первоисточники, на индексной странице — дисклеймер.
